# Cohorts and attendance

The active intake is October 2026. The `cohorts` catalogue is returned by `/api/cohorts` and admin views default to its newest entry. Applications, enrolled students, graduates, referrals and exports use the selected cohort. URLs carry `?cohort=...` between admin screens. Untagged legacy student and attendance records are interpreted as July 2026 until the production migration tags them. Recordings require an explicit cohort assignment, as described below.

Production master builds run `scripts/prepareProduction.mjs` after a successful Vite build. It reads the live Firestore rules, applies only the attendance rule changes, saves the previous rules privately, and performs the idempotent cohort migration. The migration fixes its target IDs before making changes, backs up original cohort fields, skips explicitly assigned cohorts, and never moves or renames student documents. A resumed run uses the same targets. Neither preview deployments nor local builds mutate production.

Backups are under `academyMigrations`: `cohorts-july-october-2026-v1/originalCohortFields` and `attendance-pin-rules-v1`. Only the Firebase Admin SDK can read these. Restore individual original cohort fields from those backups if rollback is needed; do not clear new registrations or move documents. Certificate profiles, public alumni and progress are not migrated. Payment code is unchanged.

## Live-session recordings

Both the live-session management page and the applications dashboard's quick publisher require an explicit recording cohort. Drafts and published records save `cohortId`; editing retains the saved assignment. The live-session management list follows its selected cohort, while an Unassigned recordings view allows administrators to classify any recording without a valid assignment. An unassigned recording remains hidden from students until corrected. The quick publisher's recording-cohort selector is independent of the dashboard's admissions filter, so switching that filter cannot silently move a typed recording to another intake.

Student queries request only published recordings for their active enrollment's cohort. The shared visibility check applies the cohort before the general audience shortcut, then retains the existing learning-method and canonical course checks. “All students” means all enrolled students in that cohort. A course recording also requires that course; a live/self-paced recording also requires the matching learning method. Displayed cards are checked again against the current enrollment so a refreshed cohort/course cannot briefly display a previous audience's cached recordings. No dates or current-intake constants determine recording membership. Shared pre-recorded curriculum remains separate from cohort-specific live recordings.

Production preparation runs `live-session-cohorts-20261020-v1` for the exact 60 historical recording IDs pinned in `server/legacy-live-recordings.mjs`. Both October 3 snapshots contained those IDs before the October intake started. The October 20 read-only audit confirmed the same IDs, July 6–September 28 session dates, and no later additions or edits. Only a missing/null/blank `cohortId` on those reviewed IDs becomes `july-2026`; every explicit assignment and every unknown/new ID stays unchanged. Titles, video/attachment links, audience settings, dates, timestamps and recording IDs are preserved. No student, attendance, progress or certificate records are changed by this backfill.

Each assignment and original-field checkpoint commit atomically under the private `academyMigrations/live-session-cohorts-20261020-v1/originalCohortFields/{recordingId}` path. Interrupted and concurrent runs use the same frozen membership and skip processed records. For an intentional rollback, inspect only checkpoints with `status: assigned`, confirm the current recording has not been reassigned since the migration, then transactionally restore the saved field value or delete `cohortId` when `hadCohortId` was false. Never recreate deleted recordings or overwrite later administrator assignments. Keep completed migration checkpoints so another deployment cannot reapply the backfill.

## Live-class attendance

All six canonical course cards appear. Cards without enrolled live-class learners in the selected cohort are disabled. Data Analytics, Web Development and Software Development require an explicit live learning method. Virtual Assistant, Cybersecurity and AI Automation default to live when no method was recorded; any explicit recorded-learning method is always excluded.

Programme identity is shared across enrollment, recording audiences, curriculum access and attendance. Cyber Security, Virtual Assistance, Software Development (Frontend), Data Analysis and AI & Automation resolve to the established canonical names. Web Development and Software Development remain separate programmes even though they share a curriculum group. Genuine curriculum subjects such as Excel, Power BI, SQL and Python retain their names.

Production preparation runs the restart-safe `canonical-programme-identity-20261003-v1` migration. It canonicalizes known programme fields and arrays in applications, adds together legacy attendance counters under one canonical key, and canonicalizes the track labels on recordings and attendance sessions. Each narrow update and its original-field backup are committed together. The frozen document manifest and checkpoints live privately under `academyMigrations/canonical-programme-identity-20261003-v1/originalProgrammeFields`. Repeated or interrupted runs do not add counters twice. Invalid counters or conflicting attendance metadata stop the affected transaction rather than discard values. Unknown course names remain unchanged.

The migration preserves student, recording, session and attendance-record document IDs, existing attendance URLs, curriculum subjects/groups, lesson/progress data, payments and certificates. Browser readers still understand legacy aliases. Dashboard attendance uses one course card and retains saved historical totals when matching attendance evidence exists; incomplete history does not reduce those totals. Attendance records are deduplicated using their parent session, course and cohort, rather than the student-based record document ID. New lecture-day writes use canonical keys; server attendance marking consolidates any remaining aliases transactionally before its single increment.

Attendance sessions are separate per course, cohort and day. Original July session IDs remain compatible. Generation uses one transaction so simultaneous requests do not increment lecture days twice. The public attendance page receives session metadata only; it does not download the student roster. Students enter their registered email and private PIN, inspect their own name/course/cohort, then confirm attendance. Server checks enforce enrollment, live format, course, cohort, date and credential version. Recording is transactional and idempotent.

PIN setup and reset are available inside the student portal for every enrolled student, including recorded-course learners and graduates. The attendance page retains its live-class eligibility checks. Both use the same private `attendanceCredentials/{applicationId}` PIN hash. Verification codes expire after ten minutes, have five attempts, and can be consumed once. PINs are salted scrypt hashes stored in server-only collections; verification is throttled by account/address and platform IP. A five-minute signed grant is needed to mark attendance. Resetting a PIN invalidates old grants and portal sessions. Contact details are not displayed on attendance pages.

## Portal sign-in and profile corrections

The portal has one email-or-phone input. `/api/portal` resolves enrolled course/cohort choices on the server; a lookup alone never authenticates a student. Accounts with a PIN must verify that PIN. Accounts without a PIN temporarily retain the existing contact-only entry, as requested for the transition, and can correct their profile before verifying their email to create a PIN. This transition remains weaker until each student creates a PIN.

Successful login creates an opaque, server-held 24-hour session with a Secure, HttpOnly, SameSite=Strict cookie. Browser storage is not an authentication source. Restoring a session rechecks enrollment eligibility and the current credential version. Creating or resetting a PIN invalidates older contact-only/PIN sessions, and the student signs in again. Existing enrollment document IDs remain the identifiers for curriculum/progress/certificate records.

My profile edits only the enrollment name, email, and phone fields. Updated contacts replace their existing lookup aliases so the previous email/phone does not remain an alternative sign-in. Edited phones require a country selection and canonical international validation; an untouched legacy phone can remain unchanged during a name/email correction. Course, cohort, enrollment/payment facts, attendance, progress and issued certificate records are preserved. Existing multiple enrollments remain explicit choices rather than being silently combined.

For PIN-protected accounts, contact changes require the current PIN and an email verification code before the database update. A changed email is verified at the proposed new address; phone-only changes verify through the private recovery address. Verification is bound to the originating session, current contacts and credential version. Confirming contact changes rotates the credential version and session; other saved logins and stale verification codes no longer work. Private contact locks prevent concurrent portal changes claiming the same new contact. Name-only changes do not need an email code.

The verified recovery email is stored privately with the PIN credential, so editing/replacing a publicly accessible application cannot redirect PIN-reset codes to an unverified email. New PIN setup and verified profile email changes establish this address. Production preparation backfills existing credentials with the registered address under `academyMigrations/portal-pin-recovery-email-20261003-v1`, retaining original-field checkpoints and preserving hashes, salts and versions. Missing private recovery bindings fail closed. Attendance setup codes also recheck the email/enrollment proof, current credential version and live-class eligibility before saving.

Portal sessions, challenges, rate limits and contact locks are browser-private collections. The production rule patch retains its exact original rules under `academyMigrations/portal-pin-private-rules-v1`. Portal/profile codes use the existing EmailJS configuration; no SMS or WhatsApp verification service is required.

Email uses the existing EmailJS service and general academy template with `email`, `to_name`, `subjectTitle`, `mainMessage`, `extraMessage`, `ctaText`, and `ctaLink`. EmailJS must allow API requests from non-browser applications. If private-key authorization is enabled there, set `EMAILJS_PRIVATE_KEY` in Netlify Functions scope (never VITE-prefixed or committed). Configure `EMAILJS_SERVICE_ID`, `EMAILJS_TEMPLATE_ID`, and `EMAILJS_PUBLIC_KEY` in Functions scope; existing `VITE_EMAILJS_*` values are also supported when available to Functions. An optional `EMAILJS_ATTENDANCE_TEMPLATE_ID` takes precedence for attendance codes. Build-only variables are insufficient for server delivery.

`GET /api/attendance` reports only whether the required email configuration is present; it does not send a message, expose credentials, or prove provider delivery. Server logs classify failures as missing function configuration, disabled server requests, authorization, quota/rate limit, template configuration, service connection, or connection/timeout errors. Raw provider responses, recipients, names, verification codes, and keys are never logged. Delivery failure stops PIN setup, removes the failed challenge, and leaves the existing PIN intact; it never falls back to unverified PIN creation. No real emails are sent by the automated test suite.

The attendance page has a visible create/reset PIN button beside the PIN field. It opens the setup panel, carries over the registered email until that address is edited, and returns students to verification after a PIN is saved. Opening another attendance link resets all verification state; pending browser requests are aborted so a previous link's details cannot remain on the new page.

## Virtual Assistant final assessment

In the admin dashboard, open **Final assessments**, verify the academy email, select the cohort and upload the private question bank JSON. Each bank needs 100 questions with a `prompt`, four `options`, and a `correct` letter from A to D. Keep the bank outside the public repository. Assessment administration uses the existing server email setup and defaults to the academy contact inbox. Netlify Functions can override it with `FINAL_ASSESSMENT_ADMIN_EMAIL`.

Students use **Take final assessment** on their dashboard. The server checks the active enrollment and student PIN, sets a 60-minute deadline when the student confirms Start, and accepts answers until that deadline. A scheduled Netlify function grades overdue attempts for students who close the page. Opening the result also finalizes an overdue attempt immediately.

Use **Approve** to lock the result for the cohort or **Reject & allow retake** to unlock one new attempt. A score appears in the student profile and in the admin certificate review. Certificate approval remains a manual decision.

## Existing access limitations

Portal sign-in and profile endpoints now use server-verified sessions. The remaining browser data access and admin screens still depend on legacy public Firestore permissions and browser-based admin roles. This change does not make the entire student database private or authenticate administrators. Existing public application/deletion and progress/certificate permissions remain for compatibility, so a separate admin-authentication and database-access migration is needed to protect all student information. Do not describe this gradual PIN feature as complete platform security.

## Future intakes

Create a `cohorts/{month-year}` document with a label and startDate, update `src/data/cohort.js` to the new active intake, and update admission validation/rules and pricing as required for that intake. Older cohorts remain selectable newest first. Do not reassign prior students or duplicate certificate/progress documents. The public alumni directory continues to show opted-in graduates from every cohort.
